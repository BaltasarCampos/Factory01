===============================================================================
1. PURPOSE AND SCOPE
===============================================================================

1.1 Purpose
  The Software Factory is an agent-driven assembly line that turns a product
  request into reviewed, tested and deployed software. The owner sets intent
  and approves every merge and release; AI agents do the rest. Every output
  must be traceable back to the request that produced it.

1.2 Constraints
  C-1  One human: the owner is product owner, code owner and on-call.
  C-2  Budget: the Claude Pro plan the owner already pays for (US$20/month,
       about GBP 19.50-21 with UK VAT). Extra spend: GBP 0. No pay-as-you-go
       API usage and no usage credits.
  C-3  Hardware: a daily-use Chromebook laptop running Crostini (Debian
       Linux container), 4 GB RAM. A larger machine may come later; the
       design must move to it unchanged.
  C-4  No compliance regime applies.
  C-5  Throughput target: 3-5 shipped work items per week.
  C-6  Products built are used only by the owner (no outside users).

1.3 Inputs
  - A product pitch of a few sentences (starts a new project)
  - Feature requests, bug reports, tech-debt tickets
  - Dependency and security updates, scanner findings, Dependabot alerts

1.4 Outputs
  - Merged pull requests, release notes, updated docs and tests
  - A deployment of the product on the laptop, behind a flag for tier 2-3

1.5 In scope (v1)
  - One reusable factory repository applied to any number of project
    repositories, one active project at a time.
  - Web back-end and front-end work of small to medium size (a ticket a
    human would finish in under a day).
  - Bug fixes and routine maintenance end to end.

1.6 Out of scope (v1)
  - Greenfield architecture decisions without the owner's sign-off.
  - Changes to auth, billing or data-deletion paths without the owner as
    named reviewer.
  - Mobile store releases and infrastructure provisioning.
  - Detailed APIs, data schemas, sizing and cost figures beyond this spec.


===============================================================================
2. DESIGN PRINCIPLES
===============================================================================

  P-1   Spec is the source of truth. Every change starts from a written spec
        with acceptance criteria; code, tests and docs derive from it.
  P-2   Small batches. Each change is reviewable in under 30 minutes
        (target: under 400 changed lines).
  P-3   Verification over generation: tests, static analysis, independent
        review, and formal verification where it pays.
  P-4   Independent checkers. The agent that verifies never shares context
        with the agent that built the change.
  P-5   The owner owns intent and every merge: the owner approves specs for
        tier 2-3 work (and skims tier 1), every merge and every release.
  P-6   Everything is an event. Each station logs structured events so any
        output can be traced to its request, prompts, tools and reviews.
  P-7   Stations are replaceable. Each has a contract (inputs, outputs,
        gate) so a model, tool or person can be swapped in.
  P-8   Fail safe, not silent. A station that cannot meet its gate escalates
        to the owner with evidence instead of retrying forever.
  P-9   Frugal by design. One agent at a time by default, cheap steps first,
        nothing hosted beyond GitHub, the laptop and the Claude Code cloud
        sessions included in the plan.
  P-10  Learn from every item, through changes the owner approves.


===============================================================================
3. SYSTEM OVERVIEW
===============================================================================

3.1 Architecture
  After a once-per-project Station 0 (Define), each work item flows through
  eight stations (1-8) like an assembly line. A control plane moves each
  item forward and records everything. A failed gate returns work to the
  earliest station that can fix it; production signals from station 8
  re-enter as new work at Intake.

3.2 Repositories
  FR-3.1  Factory repository (public, MIT licence, reused): orchestrator
          CLI, station contracts, role instructions, skills, gate policy,
          stack profiles, CI workflow templates, the constitution, general
          lessons.
  FR-3.2  Project repository (private, one per product): the product's code
          and tests plus:
            .factory/config         pinned factory version, agents: cloud|local
            .factory/brief.md       product brief written by Station 0
            .factory/lessons/       project-specific lessons (on
                                    claude/factory-log until merged)
            .factory/ops/           health summaries, incident notes,
                                    metrics reports (same)
            .factory/security/dismissals.md
            .specify/memory/constitution.md   installed from the factory
                                              release (protected)
            .specify/templates/               plan, spec and tasks templates
            specs/<issue>-<slug>/             spec.md, plan.md, tasks.md,
                                              reports/, events.jsonl
  FR-3.3  Benchmark repository (private): replay benchmark of past work
          items. MUST never be placed in the public factory repo.

3.3 Command-line tool ("factory")
  FR-3.4  Install once: clone the factory repo on the laptop; it provides
          the "factory" command.
  FR-3.5  "factory new "<few sentences>"" creates a private project repo;
          "factory adopt <repo>" attaches to an existing repo. After the
          cloud consent step (FR-3.6), both run "specify init", write
          .factory/, install every guardrail file (including the
          constitution) from the pinned factory release, install GitHub
          labels and CI workflows, create the pinned Owner inbox issue
          (8.4), and set up the working copy on the laptop. No agent installs or edits guardrail files.
  FR-3.6  Cloud consent (every project): before creating anything, "new"
          and "adopt" MUST remind the owner that agents will clone the
          project's code into Anthropic-managed cloud VMs via the Claude
          GitHub App, and ask the owner to choose cloud or local. The answer
          is saved as "agents: cloud" or "agents: local" in .factory/config.
          The dispatcher MUST NOT start a cloud session for a project whose
          config lacks this setting.
  FR-3.7  "factory run" works the project backlog through stations 1-8.
  FR-3.8  "factory upgrade" pulls a new factory release into a project as a
          pull request the owner approves. Each project pins the factory
          release (tag) it runs.
  FR-3.9  "factory deploy" re-verifies the signed approvals of every item
          it ships (FR-8.21), then pulls main, builds and restarts the app
          on the laptop and writes a health summary. Only the owner runs it;
          running it is the owner's release approval.
  FR-3.11 "factory approve <issue> [spec|waiver]" runs only on the laptop.
          It asks for the signing key's passphrase, signs an approval record
          (FR-8.19), applies the matching owner: label (owner:approved,
          owner:spec-approved or owner:waiver), and posts the signed record
          as an issue comment and in the item's event log. When approving an
          item it also confirms the item's tier: label.
  FR-3.12 "factory merge <pr>" runs only on the laptop. It re-verifies the
          item's whole chain of signed approvals and merges only if every
          one is valid; otherwise it refuses and reports the bad record.
  FR-3.13 "factory pause [station]" adds pause:line or pause:<station> to
          the Owner inbox issue. No signature is needed.
  FR-3.14 "factory resume [station]" runs only on the laptop. It asks for
          the signing key's passphrase, signs a resume record (FR-8.27),
          posts it to the Owner inbox issue and removes the pause label.

3.4 Stack profiles
  FR-3.10 A stack profile is a folder of templates and tool settings. v1
          ships a TypeScript profile only. Other languages can be added
          later without changing the stations.

4.1 Station 0 - Define
  FR-4.1  Input: the pitch; with "adopt", the existing code. The guardrail
          files and constitution are already installed by the factory tool.
  FR-4.2  MUST always ask up to 5 clarifying questions in one batch and MUST
          NOT fill gaps with its own assumptions.
  FR-4.3  Output brief (.factory/brief.md): problem, users, core use cases,
          non-goals, success measures, risk areas.
  FR-4.4  Output starter: a walking skeleton from the stack profile that
          runs, has one test, passes CI and deploys on the laptop.
  FR-4.5  Output backlog: 5-10 GitHub issues, each tagged with a risk tier.
  FR-4.6  Gate: the owner approves brief and backlog; approval moves the
          issues into Intake. Define re-runs whenever the owner revises the
          vision.

4.2 Lanes
  Lane   Used for                          Model sessions per item          Runs without a model
  ------ --------------------------------- -------------------------------- ---------------------------------
  Lean   Tier 1                            3: Spec+Plan / Build+tests /     Intake rules, lint, type check,
                                           Review                           tests, coverage, scanners,
                                                                            rebase
  Full   Tier 2 and tier 3                 6-8: every station, plus formal  Same scripted checks
                                           checks on tier 3
  Batch  Dependency bumps, copy changes    1 session for up to 5 similar    Same scripted checks
                                           items

  FR-4.7  In the lean lane, stations 2-3 share one session and station 5 is
          scripted checks plus one review session; gates are unchanged.
          Combining sessions MUST NOT skip a gate; skipping a gate requires
          a waiver the owner records.

4.3 Work item states (state: labels, set only by the dispatcher)
  state:new -> state:triaged -> state:specified -> state:spec-approved ->
  state:planned -> state:building -> state:verifying -> state:integrating ->
  state:releasing -> state:done
  state:blocked and state:escalated are reachable from any state. An item
  enters state:triaged only after owner:approved (see 8.2).

  FR-4.8  Retry policy: a failed gate returns the item to the earliest
          station that can fix it, with the failure report; after 3 failed
          attempts it escalates to the owner.
  FR-4.9  Any station may raise a question to the owner; the item waits in
          "blocked" without consuming usage.
  FR-4.10 Risk tier: Intake proposes a tier: label; the owner confirms it
          with owner:approved and may raise it at any gate; agents MUST NOT
          lower it.

6. TOOLS AND PERMISSIONS
===============================================================================

6.1 Tool set
  FR-6.1  Agents use Claude Code's own tools (Read, Write, Edit, Bash, Grep,
          Glob, subagents). The factory MUST NOT implement its own agent
          harness or core tool set (it would require paid API usage and
          lose cloud sessions).
  FR-6.2  The factory controls who uses which tool, on which files, and what
          runs around each call, through three layers committed to each
          project repo:
            1. Role definitions: .claude/agents/<role>.md (instructions,
               model, allowed tools)
            2. Permission rules: .claude/settings.json (allow/deny lists
               for tools, paths, shell commands)
            3. Hooks: scripts run before/after tool calls and at stop
  FR-6.3  Routines run without permission prompts, so these layers are the
          enforcement mechanism. Phase 0 MUST test that every deny rule
          holds inside a routine.

6.3 Hooks
  FR-6.5  Before a tool call: path guard (writes only inside the role's
          folders and the task's file list); command guard (blocks pushes
          to main or to any branch other than the one named in the station
          prompt, merges, reads of secrets, changes to owner: and state:
          labels, and removal of pause: labels).
  FR-6.6  After an edit: format and type-check the touched file.
  FR-6.7  After every call: append one line to the work item's event log
          (events.jsonl on the item's branch, or claude/factory-log after
          merge).
  FR-6.8  On stop: verify the station's output file exists and is
          complete; otherwise the session continues.
  FR-6.9  Session start: verify guardrail-file integrity (see SEC-2.4).

6.4 Factory MCP tools

8. CONTROL PLANE
===============================================================================

  FR-8.1  Orchestrator: the factory CLI picks the next ready issue by label
          and starts the item's current station as a Claude Code cloud
          session ("claude --cloud") with the station prompt; when the gate
          passes it moves the label on. Agents never decide the route.
  FR-8.2  The same orchestration logic runs as a daily cloud routine so the
          line advances with the laptop closed.
  FR-8.3  Work item store: GitHub Issues + a Project board; one issue per
          work item; owner:, state: and tier: labels (see 8.2).
  FR-8.4  Artifact store: the repository, in Spec Kit's layout: one feature
          folder per item, specs/<issue>-<slug>/, on the item's branch,
          holding spec.md, plan.md, tasks.md and reports/ (also posted as PR
          comments).
  FR-8.5  Event log: append-only events.jsonl in the item's feature folder
          until merge, then lines on claude/factory-log; Intake's entries
          start as issue comments.
  FR-8.6  Knowledge layer: CLAUDE.md, the constitution
          (.specify/memory/constitution.md), Spec Kit templates
          (.specify/templates/), role instruction files and subagent
          definitions in .claude/agents/, ADRs in /docs/adr.
  FR-8.7  Model access: Claude Pro plan; Sonnet as main model with Opus as
          advisor (see 10.2).
  FR-8.8  Kill switch: a pause:line or pause:<station> label on the pinned
          Owner inbox issue stops the line or one station at once; only a
          signed factory resume lifts it (see 8.4).

  Kind              Labels                                      Set by
  ----------------- ------------------------------------------- ----------------------------------------
  Owner gates       owner:approved (item may enter the line;    Only the owner, via factory approve
                    confirms its tier), owner:spec-approved,    (FR-3.11)
                    owner:waiver
  Workflow state    state:new ... state:done, state:blocked,    Only the dispatcher, via advance_item

  FR-8.14 Each gate passes only on its own owner: label. The dispatcher
          moves an item to state:spec-approved only on owner:spec-approved
          and never infers a gate from a state: label or another gate's
          label. The tier 1 exception (spec skimmed) applies only to an
          owner-confirmed tier:1.
  FR-8.15 Agents MUST NOT add or remove owner: or state: labels; the
          command guard enforces this (FR-6.5).
  FR-8.16 The dispatcher accepts an owner: label only with a matching
          signed record that verifies (8.3). A label without one is treated
          as tampering: the item stops and the owner is alerted.

8.3 Signed approvals
  An approval counts only if it carries the owner's signature, made with a
  key that exists only on the owner's laptop. Anyone can check it; no agent
  can create it.

  FR-8.17 Signing key: one SSH key (ed25519) used only for approvals, with
          a passphrase, stored only on the laptop. It MUST NOT enter a
          cloud environment, a repository or a secret store, and is never
          left unlocked in memory.
  FR-8.18 Public key: published in the allowed_signers file of the tagged
          factory release each project pins, and as an environment variable
          on the cloud routine, set only by the owner at claude.ai.
          Verification requires the two copies to match.
  FR-8.19 Signed record: made with "ssh-keygen -Y sign" (namespace
          factory-approve). It contains: repository, issue number, gate,
          confirmed tier, item branch, for spec approval the commit hash of
          spec.md, a timestamp and a one-time number. A record for one item
          does not verify for another; a spec approval stops verifying when
          spec.md changes; a one-time number cannot be used twice.
  FR-8.20 Cloud check: "factory dispatch" verifies every owner: label with
          "ssh-keygen -Y verify" and decides by exit code, never by model
          judgement.
  FR-8.21 Laptop check: "factory merge" and "factory deploy" re-verify the
          item's whole chain of signed approvals before anything
          irreversible. If the cloud check were bypassed, a forged approval
          could at most spend usage and open a PR the laptop refuses to
          merge.
  FR-8.22 The dispatcher flags any merge to main that has no matching
          factory merge verification record (the GitHub merge button stays
          available on GitHub Free).
  FR-8.23 Residual risks, accepted: in local mode agent sessions run on
          the same laptop as the key, protected by the passphrase (a
          hardware security key is an optional, paid upgrade); a laptop
          compromise compromises approvals; key rotation needs both a
          factory upgrade and a routine environment change by the owner.

8.4 Pause and resume (the kill switch)
  FR-8.24 Owner inbox issue: one pinned issue per project, created by
          factory new and factory adopt. It holds the pause labels and
          receives every alert: tampering, failed signatures, unsigned
          merges, critical findings, escalations.
  FR-8.25 Pause labels: pause:line (whole line) and pause:<station>, one of
          pause:intake, pause:specify, pause:plan, pause:build,
          pause:verify, pause:integrate, pause:release, pause:operate.
  FR-8.26 Adding a pause needs no signature: the owner (GitHub web or
          mobile app, or factory pause) or any agent may add one, for
          example Security or Ops on a secret leak.
  FR-8.27 Only factory resume lifts a pause. Its signed record uses
          namespace factory-approve, gate "resume", the scope, a timestamp
          and a one-time number.
  FR-8.28 Pause state comes from the inbox issue's label history: a scope
          is paused if a pause: label for it was ever added and no valid
          signed resume record for that scope came after. If the label
          disappears without one, the dispatcher restores it and alerts
          the owner.
  FR-8.29 Effects: whole line - the routine exits at once on every run, the
          dispatcher starts no new session and advance_item refuses every
          move; running sessions finish their current step but cannot
          advance (the owner may archive one at claude.ai to stop it at
          once). One station - items wait when they reach it; everything
          else keeps moving.
  FR-8.30 During a pause, factory merge and factory deploy warn and ask the
          owner to confirm, so a fix can still ship. A single item needs no
          pause label: state:blocked covers it.

11.2 Automated checks on every merge (all tiers)
  QG-1  Build and full test suite pass.
  QG-2  Every acceptance criterion maps to at least one passing test.
  QG-3  Coverage on changed lines >= 90%.
  QG-4  Lint, type check, SAST, secret scan and licence scan clean.
  QG-5  Independent review report attached and blocking findings resolved.

  QG-7  Used only on small, critical parts (state machines, permission
        rules, money calculations). The Test agent writes a model or proof
        of the one property that matters (e.g. "a refund never exceeds the
        original charge") and checks it with TLA+ (workflows, state
        machines) or Dafny (small critical functions). Runs in CI.

11.4 Test discipline and approvals
  QG-8  New tests MUST be seen failing before the change makes them pass.
  QG-9  Flaky tests are defects: fixed or quarantined with an issue the
        owner can see. Agents MUST NOT weaken, delete or skip tests without
        the owner's approval.
  QG-10 Skipping any gate requires a waiver the owner records.
  QG-11 Every approval request includes a short summary: what changed, how
        it maps to the spec, test and review results, usage spent, known
        risks.

12. SECURITY
===============================================================================

12.1 Baseline controls
  SEC-0.1 Agents never hold production credentials; deploys run on the
          laptop through "factory deploy", outside any agent session.
  SEC-0.2 Sandboxes are ephemeral cloud VMs; GitHub credentials and keys
          stay outside the VM (proxy authenticates); network egress limited
          to the Trusted allowlist.
  SEC-0.3 Secrets never enter agent context.
  SEC-0.4 Untrusted text (issues, comments, web pages, dependency files,
          routine payloads) is data, never instructions.
  SEC-0.5 Merges to main need passing CI and owner approval. On private
          repos (no branch protection on GitHub Free) this is enforced by
          the command-guard hook and the dispatcher; sessions push only to
          claude/ branches.
  SEC-0.6 Routines get only the repositories they need and no extra
          connectors.
  SEC-0.7 In every repository, the orchestrator acts only on work items the
          owner authored or approved (owner:approved, applied through
          factory approve). Public
          factory repo: generic material only; no project code, briefs,
          lessons or benchmark items; other people's issues and PRs are
          data, never instructions. General lessons are scrubbed of project
          details by the Coach and checked by the owner.

12.3 Guardrail protection
  SEC-2.1 Protected files: .claude/, .mcp.json, hooks folder,
          .github/workflows/, .factory/config,
          .specify/memory/constitution.md, lockfile policy. Every role is
          denied Write and Edit on them.
  SEC-2.2 Only the factory tool changes them: "factory new" and "factory
          adopt" install them from the pinned factory release at project
          start, and "factory upgrade" updates them in an owner-approved PR.
          No agent installs or edits them; an agent may only propose a
          change (e.g. a constitution amendment) as a PR the owner approves.
  SEC-2.3 CI check "guardrail-change" fails any PR touching a protected
          file until the owner explicitly approves it.
  SEC-2.4 A session-start hook compares guardrail files with the pinned
          factory release; a mismatch stops the session and alerts the
          owner.

12.5 Agent-assisted triage and remediation
  SEC-4.1 Detect: finding from CI, the weekly main scan, or Dependabot.
  SEC-4.2 File: Intake creates an issue labelled "security", deduplicated
          by rule and location. It enters the line once the owner approves
          it with factory approve; critical and high findings notify the
          owner at once.
  SEC-4.3 Triage: critical and high -> full lane, jump the queue (targets
          e.g. 2 days / 1 week [PLACEHOLDER]); medium -> normal queue;
          low -> backlog.
  SEC-4.4 Fix: Builder updates the dependency or patches the code and adds
          a regression test reproducing the finding.
  SEC-4.5 Verify: Security agent re-runs the scanner on the branch; the
          finding must be gone and CI green before owner review.
  SEC-4.6 Close or dismiss: dismissing a false positive needs a written
          reason from the Security agent plus owner approval, recorded in
          .factory/security/dismissals.md with a re-check date.
  SEC-4.7 Secret leak: Security or Ops adds pause:line, the owner rotates
          the secret, the Ops agent writes an incident note with cause and
          the new check that would have caught it, and the owner lifts the
          pause with factory resume.

12.6 Governance
  GOV-1  Full audit trail per work item: prompts, tool calls, diffs,
         reports, approvals.
  GOV-2  Agent-authored commits are labelled with agent role and work item
         id.
  GOV-3  Risk tiers and approval rules are policy as code, reviewed like
         any other code.
  GOV-4  The constitution implements this design. Where they disagree, the
         design is corrected first and the constitution amended to match.

13. SELF-IMPROVEMENT AND SELF-RUNNING
===============================================================================

  FR-13.1 Capture: each station logs gate results, rework loops and owner
          review comments to the event log.
  FR-13.2 Retrospect: weekly, the Coach reads the log and writes lessons per
          role (what failed, what the owner corrected, what repeated).
  FR-13.3 Propose: project-specific lessons go to .factory/lessons/ on
          claude/factory-log. Changes to role instruction files,
          checklists, skills or lint rules are PRs to the factory repo
          (role files are guardrail files in every project); they reach
          projects through factory upgrade.
  FR-13.4 Evaluate: the changed role is replayed on a benchmark of past
          items (start with 5-10) and must not lower first-pass gate rate.
  FR-13.5 Adopt or discard: the owner decides; role instructions are
          versioned so a regression reverts in one step.
  FR-13.6 Lessons at two levels: project-specific lessons stay in
          .factory/lessons/ (via claude/factory-log); general lessons go to the factory repo as PRs
          and must pass the replay benchmark (kept in the private benchmark
          repo).
  FR-13.7 Guardrails: the Coach edits instructions only, never gates,
          permissions, budgets, guardrail files or the constitution; it
          cannot approve its own PRs. The replay benchmark only grows:
          items are never removed or edited inside a Coach change; only the
          owner retires an obsolete item, in a separate change.
  FR-13.8 Self-running: a daily cloud routine runs the orchestrator; a
          GitHub trigger starts the Reviewer when a PR opens. Each run works
          ready items until an owner gate, the usage limit or a cap, then
          leaves a summary on the issue.

19. CONSIDERED AND DEFERRED: LLM GATEWAY
===============================================================================

  Decision (1 October 2026): an LLM gateway as a control layer for model
  routing, access control, cost and rate limits, logging and tracing,
  guardrails, and fallbacks and retries is DEFERRED.

  Reasons
  - Stations run as Claude Code cloud sessions and routines on Anthropic's
    infrastructure, which call the model from there; a gateway would see
    only the local fallback path.
  - Gateway credentials replace the subscription login and are billed per
    token, breaking the GBP 0 extra-cost constraint (C-2). Hosting does not
    fit the 4 GB laptop (C-3), and the gateway needs upkeep as Claude Code
    evolves.
  - Gateways cannot route Claude Code to non-Claude models.

  Covered today by
  - Model routing: model per role; Sonnet main with Opus advisor.
  - Security and access control: credentials outside cloud VMs; per-role
    permissions; network allowlist.
  - Cost and rate limits: Pro plan limits; usage logged per item; one
    session at a time; kill switch.
  - Logging and tracing: hook-written event log; session transcripts.
    Gap: full prompt/response capture.
  - Guardrails: hooks and deny rules where tools run.
  - Fallbacks and retries: Claude Code retries; dispatcher retry and
    escalation; local fallback.

  Instead
  - The factory dispatcher is the control layer (per-item usage budget,
    retries, kill switch).
  - Phase 0 checks Claude Code's OpenTelemetry export from cloud sessions
    to close the tracing gap.
  - Model settings stay in Claude Code configuration, so a gateway can be
    added later by configuration only.

  Revisit when: API billing is adopted, a second user joins, provider
  switching is needed, or a compliance regime requires central logging of
  every request. Options then: Anthropic's Claude apps gateway, or a
  third-party gateway exposing an Anthropic-format endpoint.
